# Learning Management System API

A REST API for a Learning Management System (LMS). The project is being built
to support students, instructors, and administrators with courses, enrollment,
learning materials, assignments, grading, and related academic workflows.

## Current status

The project is under active development. Current features include user
registration and login, department and course management, and enrollment
applications with administrator approval.

## Technology

| Area | Technology |
| --- | --- |
| Runtime | Node.js 24 |
| Language | TypeScript |
| HTTP framework | Express 5 |
| Database | PostgreSQL |
| ORM and migrations | TypeORM |
| Password hashing | bcryptjs |
| Environment validation | Joi |
| Package manager | pnpm |

## Prerequisites

- Node.js 24
- pnpm
- PostgreSQL 17 (or Docker to run it locally)

## Getting started

1. Install dependencies:

   ```powershell
   pnpm install
   ```

2. Start a local PostgreSQL database with Docker:

   ```powershell
   docker run -d `
     --name lms-postgres `
     -e POSTGRES_USER=lms_admin `
     -e POSTGRES_PASSWORD=your_secure_password `
     -e POSTGRES_DB=lms_db `
     -p 5432:5432 `
     -v lms_postgres_data:/var/lib/postgresql `
     postgres:17
   ```

3. Copy `.env.example` to `.env`. Set `DATABASE_URL` to match the database
   credentials above, and replace both JWT secret placeholders with unique,
   random values of at least 32 characters. These secrets are required by the
   environment configuration. Access tokens are signed with `JWT_SECRET` and
   must have a lifetime between 1 minute and 1 hour. Configure `SENDGRID_API_KEY`
   and `MAIL_DEFAULT_FROM` to send approval emails. Set `ACCOUNT_SETUP_URL` to
   the frontend password setup page; it defaults to `CORS_ORIGIN/set-password`.

4. Create the UUID extension used by the initial migration, then run all pending
   migrations:

   ```powershell
   docker exec lms-postgres psql -U lms_admin -d lms_db -c 'CREATE EXTENSION IF NOT EXISTS "uuid-ossp";'
   pnpm typeorm migration:run -d src/config/database.ts
   ```

5. Start the development server:

   ```powershell
   pnpm dev
   ```

The API listens on port `4000` by default. Change `PORT` in `.env` to use a
different port.

## Updating an existing database

Schema changes are applied through TypeORM migrations; automatic schema
synchronization is disabled. To update a database with the latest code:

1. Back up the database, especially before production updates.
2. Set `DATABASE_URL` (and `DATABASE_SSL`, if needed) in `.env` to the target
   database.
3. Check which migrations are pending:

   ```powershell
   pnpm typeorm migration:show -d src/config/database.ts
   ```

4. Apply the pending migrations:

   ```powershell
   pnpm typeorm migration:run -d src/config/database.ts
   ```

This applies migrations that have not yet been recorded as complete; do not
manually recreate tables or edit the migration history. For future entity
changes, generate and review a migration, commit it with the code change, then
run the migration command above in each environment:

```powershell
pnpm migration:generate
```

The package script writes the generated migration under `src/migrations` with
the `AutoGenerated` name prefix.
Do not enable TypeORM `synchronize` as a substitute.

For browser-based local development, set `CORS_ORIGIN` to the frontend origin
(for example, `http://localhost:3000` for Vite). Restart the API after changing
it. This setting allows that origin to make API requests; it does not affect
requests from tools such as Postman.

## Endpoints

Register a user with `POST /api/users`. Registration always assigns the `user`
role; the public endpoint does not accept role changes:

```json
{
  "email": "student@example.com",
  "firstName": "Taylor",
  "lastName": "Student",
  "password": "replace-with-a-strong-password"
}
```

The API returns the created user's public data with HTTP status `201`.

Prospective students can submit an enrollment application without creating an
account first:

```json
{
  "firstName": "Taylor",
  "lastName": "Student",
  "email": "taylor@example.com",
  "departmentId": "department-uuid",
  "courseIds": ["course-uuid"]
}
```

Submit it to `POST /api/enrollments`. The response contains a tracking number
for `GET /api/enrollments/status/{trackingNumber}`. Department and course
choices are available from `GET /api/departments` and
`GET /api/courses?departmentId={departmentId}`. A course must be assigned to
at least one department when created; it may be assigned to multiple
departments. `GET /api/courses` lists all courses; pass `departmentId` to
filter for enrollment. Admins can update department assignments on existing
courses with `PATCH /api/courses/{courseId}/departments`.

Admins can review pending applications through
`GET /api/enrollments/admin/pending`. Approve or reject one with
`POST /api/enrollments/admin/{applicationId}/approve` or
`POST /api/enrollments/admin/{applicationId}/reject`. On approval, the API
creates/promotes the user to `student`, assigns a student ID, and creates the
requested course enrollments. A new student receives an expiring,
single-use password-setup link by email. The frontend submits that token and
the chosen password to `POST /api/users/complete-setup`. If email delivery
fails, admins can retry with
`POST /api/enrollments/admin/{applicationId}/resend-approval-email`.

Log in with `POST /api/users/login` using the registered email and password.
The response contains a short-lived access token and a refresh token. Send the
access token on protected requests as `Authorization: Bearer <accessToken>`.
When it expires, exchange the current refresh token at `POST /api/users/refresh`:

```json
{
  "refreshToken": "<refreshToken>"
}
```

The response contains a new access token and a **rotated** refresh token. Store
the new refresh token and discard the old one; each refresh token can be used
only once. Each rotation renews its idle expiry; `JWT_REFRESH_EXPIRES_IN`
defaults to seven days. These endpoints currently exchange refresh tokens in
JSON, so treat them as credentials and avoid browser storage such as
`localStorage`; browser deployments should use server-set Secure, HttpOnly
cookies with appropriate CSRF protection. `POST /api/users/logout` accepts the
current refresh token in the same JSON shape and revokes it. Any already issued
access token remains valid until its short expiration.

Only active users with the `admin` role can create resources:

- `POST /api/departments` with `name`, `code`, and optional `description`
- `POST /api/courses` with `name`, `code`, required `departmentIds`, and
  optional `description`
- `PATCH /api/courses/{courseId}/departments` with required `departmentIds`

An administrator account must be provisioned by a trusted operator; never
promote accounts through the public registration endpoint. Apply migrations
before using department or course creation.

To create the initial administrator, set `ADMIN_EMAIL`, `ADMIN_PASSWORD`,
`ADMIN_FIRST_NAME`, and `ADMIN_LAST_NAME` in `.env`, then run:

```powershell
pnpm seed:admin
```

The seed hashes the password and does not change an existing admin account. If
the configured email belongs to a non-admin account, the seed exits with an
error rather than promoting it.

In production, serve the API over TLS and enforce shared rate limiting for
`POST /api/users/login` at the gateway or load balancer.
